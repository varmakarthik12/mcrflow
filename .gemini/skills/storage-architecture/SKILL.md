# MCRFlow Storage Separation Architecture

This skill defines the mandatory storage architecture and directory separation rules for MCRFlow across bare-metal, development, and containerized deployments.

## 1. Architectural Philosophy: Strict Read-Only Media vs. Writable Runtime Data

MCRFlow enforces a strict boundary between operator source content and system runtime artifacts:

```
c:\sources\stream (or /app in container)
├── media/               <-- [READ-ONLY] Operator source media ONLY (movies, promos, ads)
│   ├── sample_movie.mp4
│   └── sample_broadcast_promo.mp4
└── data/                <-- [READ-WRITE] System runtime data and generated artifacts ONLY
    ├── mcrflow.db       (SQLite primary database in WAL mode)
    ├── logos/           (Station logos, channel graphics, overlays)
    ├── logs/            (Channel playout FFmpeg logs, service telemetry)
    ├── hls/             (Live HLS manifests and MPEG-TS segments)
    └── epg/             (Exported XMLTV schedules and broadcast guides)
```

---

## 2. Directory Specifications & Invariants

### 2.1 The `media/` Directory (Strictly Read-Only)

- **Purpose**: Exclusively for source video and audio media files loaded by broadcast operators (movies, episodic programming, interstitial promos, commercial spots).
- **Access Level**: Read-Only (`r--`). MCRFlow services must never attempt to create directories or write files inside `media/`.
- **Default Path**: `./media` relative to the working directory.
- **Configuration**:
  - CLI Flag: `-media-dir <path>`
  - Environment Variable: `MCRFLOW_MEDIA_DIR=<path>`
- **Docker Mount**: Mounted as a read-only volume (e.g. `-v /host/media:/app/media:ro`).

> [!CAUTION]
> Never write logs, generated playlists, temporary files, uploads, or databases to `media/`. Violating this breaks production environments where media storage resides on read-only NAS/SAN mounts or Object Storage gateways.

---

### 2.2 The `data/` Directory (Read-Write Runtime)

- **Purpose**: All persistent and transient state generated by MCRFlow.
- **Access Level**: Read-Write (`rw-`).
- **Default Path**: `./data` relative to the working directory.
- **Configuration**:
  - CLI Flag: `-data-dir <path>`
  - Environment Variable: `MCRFLOW_DATA_DIR=<path>`
- **Docker Mount**: Mounted as a persistent writable volume (e.g. `-v mcrflow-data:/app/data`).

#### Subdirectory Layout inside `data/`:
1. **`data/mcrflow.db`**: Primary SQLite database configured with `WAL` journal mode and `busy_timeout=5000`.
2. **`data/logos/`**: Station bug, channel icon, and overlay image assets (PNG, JPEG, SVG) uploaded via the API or UI.
3. **`data/logs/`**: Playout engine and background worker process logs (e.g. `ch-01_playout.log`).
4. **`data/hls/`**: Dynamic sliding-window HLS playlists (`playlist.m3u8`) and `.ts` transport stream segments generated by FFmpeg or the internal HLS engine.
5. **`data/epg/`**: Cached and exported XMLTV electronic program guides (`<channel_id>.xml`).

## 3. Code Implementation Rules

When authoring backend Go code or frontend React code:

1. **Storage Manager Initialization**:
   Always pass both `mediaDir` and `dataDir` distinctly to internal services (`playoutEng`, `hlsMgr`, `storageMgr`).
2. **Logo Asset Handling**:
   - Logo uploads must save to `filepath.Join(dataDir, "logos", filename)`.
   - The returned and stored path must start with `data/logos/`.
   - The HTTP server must serve `/data/logos/*` directly from `filepath.Join(dataDir, "logos")`.
3. **Playout & FFmpeg Output**:
   - Playout process stdout/stderr logs must pipe to `filepath.Join(dataDir, "logs", channelID+"_playout.log")`.
   - Playout HLS live segments must output to `filepath.Join(dataDir, "hls", channelID)`.
4. **File Pickers & Browsers**:
   - The Schedule and Media file pickers only browse the read-only `mediaDir` for video playout assets.
